# AlphaAgent 现在做到哪里了，接下来还要做什么

更新日期：2026-10-11。本次已补齐动态双股比较与5.3策略软件执行链；真实数据的完整性另外记录。最终验证见 [功能收尾记录](superpowers/plans/2026-10-11-alphaagent-functional-results.md)。

这份说明以当前代码、当前本地服务中的真实报告和已有验收记录为依据。它描述的是实际状态；之前为面试制作的“假设项目全部完成”的介绍，不能作为功能已经落地的证明。

## 1. 先用一句话说明现在的系统

**现在的 AlphaAgent 已有单股研究、动态双股比较、情景重算、追问、历史及导出的完整功能链。五角色真实调用，数字由 Python 计算。年度选股、公司行为账本、三成本重算与完整回测报告的软件也已接通；真实全市场历史输入尚未通过准入，因此不能宣称正式全市场收益已经可用。**

可以这样理解它的价值：以前研究一家公司，要分别找行情、翻财报、算指标、看公告，再整理成报告。现在用户输入公司名称或代码，系统帮你完成一部分资料收集、计算、解释和整理，还能告诉你某条判断用了哪些资料、哪些信息没有取到。

它目前比较适合回答这些问题：

- “帮我研究一下美的集团，看看经营表现、估值和风险。”
- “这家公司的利润、营收和现金流表现怎么样？哪些地方需要继续查证？”
- “假设增长率或折现率变了，DCF 情景结果会怎么变化？”
- “换一组均线参数或交易成本，单股历史模拟会怎么变化？”
- “这个结论依据什么？我能不能打开证据看一眼？”
- “接着刚才的研究再解释一下估值假设和风险。”

它能帮助用户缩短研究和核查的路径。对于缺资料、口径有分歧或模型依据不够的地方，目前会保留限制，不能把报告生成成功理解成投资结论已经被证明。

## 5. 数据拿回来以后，是怎么处理的

用“研究美的集团”这个请求举例，主流程大致是这样：

1. **先理解问题。** Planner 判断是不是单股研究、研究对象是谁、重点是什么；范围不支持或对象不明确时给出对应状态。
2. **确认证券身份。** 用证券搜索和公司资料确定代码、市场和财务类型。名称含糊时要求澄清，不随便选一只。
3. **采集数据并保存原始响应。** 获取报价、日线、财报、估值等，记录查询时间、来源和内容哈希。关键价格失败会阻止出稿；可选数据失败会留下模块缺项。
4. **用 Python 处理数值。** 处理报告期、披露日期、字段别名、单位和适用性，再计算指标、DCF 和单股模拟。
5. **整理证据。** 将计算结果整理成带编号的事实，将有限范围内的公告和财报文本切片、检索，供分析和复核使用。
6. **让模型解释和复核。** Analyst 形成有引用的候选结论，Verifier 检查依据和推断，Writer 组织允许采用的结论。
7. **保存报告版本。** 图表展示确定性计算结果，解释绑定证据，执行记录和来源继续保留。

整个原则是：**模型负责理解和解释，计算工具负责数字。**原型提供产品形态和展示参考，原型的计算代码不得移植或复制。

例如 TTM，当前采用“最近完整年报 + 本年累计 − 上年同期累计”的计算方式。假设上年全年利润 100、本年上半年 60、上年上半年 40，那么 TTM 是 120。这只是公式说明中的假设数字，不是某家公司的实际数据。

单季值由累计报表差分取得。当前最新研究中的 ROE 明确为“累计归母净利 / 期初期末平均归母权益”，没有把半年值自动年化，也不能直接当成披露的加权平均 ROE。PE 自算也需要对应价格、股本和 TTM 口径。

数值核对需要分清三层：

- 手算样本和边界测试：检查公式和程序有没有明显算错。
- 独立权威口径核对：确认取对了字段、报告期、单位和股本等。
- 同输入复算和哈希一致：确认结果可以重现。

这三层解决的问题不同。模型复核、供应商之间数值一致或哈希校验，都不能独自证明金融口径正确。

## 6. 多 Agent 现在到底怎么工作

当前五个角色使用的是同一个已配置模型 `deepseek-flash`，通过不同提示词和 Pydantic 输出契约承担不同任务，并非五个不同模型。

| 角色 | 当前实际职责 | 能力边界 |
| --- | --- | --- |
| Planner | 识别对象、研究范围、重点及澄清需求 | 还没有生成可以自由调整的研究任务图 |
| Data | 输出受限的工具计划，由 Supervisor 执行 | 采集、计算、披露检索三项基础工具固定必需，动态选工具的空间很小 |
| Analyst | 阅读证据包，形成二至六条带引用的结论 | 依赖当前提供的事实和片段，还不会自己发起补查 |
| Verifier | 检查每条结论的证据支持、主体、时间、单位和推断 | 属于单独调用的角色复核；同模型复核不是独立机构数值验证 |
| Writer | 选择通过复核的结论、安排顺序和标题 | 当前写作空间较小，不能自由增加事实或改写出新的数字 |

所以，现在可以说已经有真实多角色协作，LLM 在问题理解、材料解释和推断复核中发挥作用。不过，Data 的动态决策能力和 Writer 的组织写作能力还没有充分展开。

### 共享证据，是不是把所有东西都发给所有角色？

不是。资料统一存，Supervisor 按角色构造上下文。

- Planner 主要看问题、显式代码和有限父任务上下文。
- Data 主要看计划和已确认的证券身份。
- Analyst 和 Verifier 共享本轮整理出的事实、检索片段、核对结果、覆盖情况、日期和方法说明；Verifier 另外看到候选结论。
- Writer 看到候选结论及允许采用的编号，输出受复核结果约束。

结构化事实使用 F 类编号，文本片段使用 J 类编号。它们与保存的资料关联，文本片段还保留字符位置。完整 K 线序列、全部模拟明细和所有原始财报，并没有全部放入模型上下文。

目前检索是有范围限制的词法检索：最多两篇公告正文，加上最近几个报告期的利润表文本，通常选出最多六个片段。尚未接入 Embedding、向量数据库或全量公司资料库。

### 有 Agent Loop 吗？是黑板模式吗？

这里要区分原底盘和当前量化主流程。

原 deepsearch 有“收集证据 → 分析 → 复审 → 决定是否补查”的受约束研究循环；Investigation 也已有研究缺口、信息增益和预算控制等基础。

**当前量化页面的五角色流程，没有接入这套自动补证循环。**它按预定顺序运行；Verifier 拒绝某条结论后，不会自动调工具补材料、重新分析。调用失败后的重试属于容错；用户追问属于用户触发的新研究。

当前量化架构更适合叫“Supervisor 集中编排、共享证据和持久化任务状态的多角色工作流”。完整黑板机制需要共享假设、待解决问题、冲突和证据状态，再按知识缺口调度角色；这些尚未在量化主链路实现。黑板与 Agent Loop 可以结合，但接入循环不要求先重建成完整黑板系统。

## 7. 状态怎么保存，失败怎么恢复

当前本地运行使用 SQLite，代码通过 SQLAlchemy 管理任务。状态存到 `inv_quant_research_run` 表，较大的资料存到现有 Blob 文件存储。

你可以把它理解成两部分：

| 存储位置 | 保存内容 |
| --- | --- |
| 数据库 | 任务编号、原请求、父任务、计划、步骤状态、调用记录、错误、Token 用量、资料引用、报告引用及实现指纹等 |
| Blob 文件存储 | 原始响应、工具输入输出、模型结构化输出、检索文本和最终报告等 |

Blob 按内容计算 SHA-256，读取时校验内容。数据库状态在阶段切换、调用开始和结束等位置通过事务保存。它是任务状态快照加调用轨迹，不是给每个模型直接开放一个可以随意读写的数据库。

假设取数和计算已完成，Analyst 遇到网络错误，点击继续后会检查已有步骤：请求内容完全一致、已经完成的结果可以复用，失败或未完成的调用重新执行。服务重启时，遗留运行中任务会标为中断，再通过恢复入口继续。

完成的报告不能原地覆盖。改 DCF 或均线参数会生成新版本，旧版本保留，旧模型解读不会复制到已改变数值的新情景中。代码实现指纹发生变化时，当前流程要求新建任务，避免混合计算版本。

**状态保存不等于长期记忆。**当前追问主要继承父任务的股票、问题、重点和参数，不会自动记住用户所有历史聊天。追问会重新取数，父任务旧数值不作为新一轮事实。

## 8. 现在说的“实时”，到底实时到什么程度

有三件事需要分开：

| 行为 | 当前含义 |
| --- | --- |
| 页面报价刷新 | 每 30 秒请求上游最新报价，也可手动刷新；不是 Tick 推送或确定延迟的行情服务 |
| 新建研究或“重新采集并研究” | 当次请求重新取资料，再生成一个绑定本次输入的报告 |
| 打开历史报告或改参数 | 回看使用当时保存的资料；参数重算也复用同批输入，不代表重新采集 |

报告需要保留自己的输入版本，这样才能知道当时为什么得出那个结果。最新报价和报告时点同时展示，是为了兼顾当前观察和结果追溯。

2026-10-10 核对的四份样本报告，价格和估值日期是 2026-10-09，最新财报期是 2026-06-30，两融各自截至 10 月 8 日或 9 日。2026-10-10 是周末，重新查询也不会凭空产生新的交易价格；财报更不会每秒更新。

若以后希望价格变化自动触发 PE、DCF 比较或解读更新，需要增加按数据类型划分的刷新与重算机制，并保留版本关系。模型无需跟着每次报价都调用。

| 数据覆盖和口径还不够稳定 | 有些股票研究能完成，但某个图或指标缺资料 | 补来源、字段映射、期间和单位校验，建立逐模块覆盖清单及明确降级状态 |
| 最新研究与旧比较链路未统一 | 单股可以动态研究，任意两股比较却可能被旧目录限制 | 把比较接到统一研究服务，用两份新采集子报告形成共同期间和口径的对照 |
| 量化 Agent Loop 未接入 | 模型发现依据不足，也不会主动找下一份材料 | 增加结构化研究缺口、工具路由、补证和重分析循环，复用原底盘能适配的控制能力 |
| 原始公告与指标独立核对不足 | 两个供应商一致，仍可能一起用错口径 | 扩展原始披露解析、字段和页码定位，保存计算方法与独立参考，按指标定义容差 |
| 5.2 历史数据不完整 | 正式回测报告仍受阻，收益图不能填数 | 补齐历史身份、财报修订、公司行为、交易限制和基准的完整证据 |
| 完整真实回测仍待数据准入 | 策略软件链已接通，完整真实输入和独立结果参考仍缺 | 继续取得历史档案并核对；合格包接入后使用现有隔离执行链，不以合成收益替代 |
| 量化主链路缺生产运行闭环 | 多人并发、重启、长期采集和持续发布还缺保障 | 接入可靠任务队列、权限、监控、备份恢复、版本化评测和发布流程 |

这不是多加几张图就能解决的问题。有的是软件还没接好，有的是必须取得并审核外部数据，还有的是方法本身对该公司不适用。

例如银行没有工业 DCF，正确处理是保留“不适用”，未来需要银行估值时另做适用模型。格力、茅台缺字段，则需要先判断原始披露到底是明确为零、未披露，还是供应商漏取，不能直接补零让图出现。

## 10. 5.2 为什么还没完成，要怎样补

5.2 是正式回测前的历史数据准备与准入。它需要回答的核心问题是：**在某个历史时刻，研究者究竟知道什么，那时究竟能交易什么？**

已有采集、分区、续采、覆盖账本和严格检查，不代表需要的真实资料已经齐全。下面是主要工作。

### A. 历史名单和证券身份

不能拿今天还上市的股票，直接代表五年前全市场。要保留上市、退市、改码、主体延续和特殊状态的历史区间，并独立核对名单范围。

已完成一项官方改码取证，也保留了原有日期冲突。后续需要逐项补证，确认准确生效边界；仍不确定的身份继续显示未知，不悄悄排除。

### B. 全市场历史财报修订链

今天查到的“2023 年利润”可能已经修订过，不能直接当成 2024 年某天当时能看到的数。

需要按证券和报告期保存首次披露、后续修订、公开可得时间及其精度、原始文档、字段值、单位、合并范围和版本关系。查询历史时点时，只能选当时已经公开的版本。

只有公告日期、没有准确时刻时，要制定保守的可得时间规则并标明精度，不能声称已证明某个盘中时点可得。软件字段和筛选逻辑可以开发，缺失的旧版本原文和时间依据仍要实际取得。

### C. 完整公司行为

除了现金分红，还要覆盖送转、配股、合并及退市安排等事件，并记录相应的登记、生效、支付或上市日期、条款和原文。

目前有部分分红观察，但“接口返回空”不证明这段时间没有事件。后续需要覆盖账本和完整性依据，再把现金、股数及持仓变化落实到交易账本。前复权价格不能替代这一步。

### D. 历史成交限制

策略发出买入信号，不代表那个价格一定能成交。需要按当时有效的规则和证券状态，核实停复牌、买卖方向限制、价格限制以及执行时点的可成交证据。

后续应将规则按生效区间保存，将逐日限制和执行证据接入账本，记录成交、拒单、现金及剩余仓位。仅有日线收盘价时，不能推断所有开盘成交情况。

### E. 全收益及独立核对

价格指数和全收益指数要分别处理。全收益涉及分红再投资等处理，不能拿价格指数直接冒充。

现有历史样本已保存官方沪深 300 价格和 H00300 全收益序列，各 1,211 个交易日；价格指数与 BaoStock 的逐日核对记录为 1,211 项一致。H00300 的独立交叉核对仍缺，策略自身的全收益也尚未完整实现和验证。

下一步要取得口径可确认的独立参考，明确收益类型、再投资、费用和现金处理，预先设定容差，再核对策略和基准各自结果。

### 当前历史采集量应该怎样理解

改码取证验收时，新版计划涉及 5,414 个代码、5,413 个身份观察、100,303 个分区，先采集了 24 份响应。2026-10-11 又完成两批真实续采：第一批成功 23 份、失败 1 项；第二批成功 24 份并补回该失败项，累计 71 份，剩余 100,232 个分区。旧版另外保留 48 份响应，两版不能直接相加当成独立覆盖。

本轮还修复了准入内核的一处缺口：审核记录指向的原文和参考原文现在都要实际读取并验哈希，不能只凭记录中写了 MATCH 就通过；年度筛选也明确保存 TTM 归母净利润。具体实施和验收见[5.2 原始证据门禁与真实续采结果](superpowers/plans/2026-10-11-alphaagent-52-evidence-results.md)。这些加强了准入检查，但没有替代尚缺的真实档案。

**这证明全市场采集工具已经开始真实工作，不证明全市场数据已经采完。真实完整数据包尚未通过严格准入，5.2 仍未完成。**

免费来源可以继续推进采集和核查，但部分旧版本、准确发布时间和完整成交档案能否取得，必须实际验证。普通字段多的付费 API 也未必具备这些档案。

## 11. 建议接下来怎么做，按什么顺序

用户已明确：缺数据可以预留，先把原计划软件功能接齐。以下区分已完成的软件、真实数据补充和额外增强；继续沿用 Vue 3、多 Agent、原型展示、免费来源优先和不移植原型算法等约束。

### 第一优先：把动态单股的数据质量做扎实

先复查美的、格力、茅台、银行，再增加不同行业、上市时间较短和数据不完整的样本。逐模块建立“取得了什么、缺什么、方法是否适用”的覆盖清单。

重点补财务字段和官方披露定位，处理零值与缺失的区别、报告期和单位差异、来源冲突、行业适用性，以及上游失败时的替代来源。替代来源必须留身份和口径记录，不能静默混用。

**验收：**适用模块有真实输入；不适用模块明确说明；无法取得的模块有具体原因。关键指标具备手算、独立参考和复算三类证据，而不仅是页面有数字。

### 动态双股比较：本轮已接通

已经复用统一证券解析和研究服务，为双方创建共同请求时点的子任务，分别保留数据日期、调用及来源。比较层先核对口径，再展示差异与各股经过角色复核的解读。原型五维和既有指标都保留，不形成投资排名。

报告期、行业、单位或样本覆盖不一致时给出口径差异；一方失败后只恢复未完成部分。真实验收为中际旭创与新易盛，均有五角色成功调用，640个共同交易日。一侧报价超时后恢复成功，另一侧没有重跑。三只以上属于后续扩展。

**验收：**挑两只未预先放入首页卡片的股票，从输入到双方新取数、比较表、证据、历史回看和导出全部跑通；同时测试同名、重复标的、缺数据和不可比口径。

### 第三优先：接入一个小范围、受约束的 Agent Loop

先围绕“解释利润与现金流变化”或“解释估值差异”做补证闭环，不一开始开放无限搜索和任意代码执行。

让 Verifier 输出结构化缺口，包括缺什么、为什么影响结论、需要哪类材料。Supervisor 据此选择允许的工具，新增证据后再分析和复核。复用原底盘的预算、缺口和信息增益控制时，需要适配量化合同和来源规则，不能仅把旧循环直接套上。

为循环设置可配置的少量轮次、调用和时间预算；充分支持、达到预算、连续无新信息或来源失败时结束，并解释剩余缺口。

**验收：**设计确实需要第二轮资料的样本，能看到“缺口 → 新工具调用 → 新证据 → 修订结论”的真实记录；与固定流程比较证据覆盖、错误支持率、延迟和费用，证明新增循环有价值。

### 持续推进：5.2 历史档案与独立核对

这条线可以持续按有限批次推进，不必等全市场档案齐备才改善单股体验或 Agent。先选一个明确的小范围和固定历史窗口，验证完整的数据包，再按股票、年份和资料类型扩展。

小范围通过时，只能声称该范围通过；原计划的全市场目标仍需全范围覆盖。不能因为范围难而悄悄把全市场改成少数股票。

**验收：**每个必要分区有来源和审核记录，修订和时间边界可追溯，公司行为与限制有覆盖依据，冲突已解决或继续阻止准入。只有原范围全部通过，才能勾选 5.2 整体完成。

### 5.3：软件执行链已接通，真实数据仍待准入

数据通过准入后，已经可以直接进入年度选股、模拟成交、现金持仓账本、公司行为、费用和绩效的完整执行链。由固定、禁网、有限资源的子进程执行；隔离测试包已验证页面四曲线、年度名单和离线复算。测试包不安装到演示数据库。特殊合并、碎股及持有期差异税额等条款不明确时继续拒绝，不能宣称支持所有公司行为。

保持信号先于执行、价格和全收益区分、交易成本独立情景重算，展示真实选股条件、五项绩效、净值及年度持仓。图表沿用原型，数值来自新实现和审核过的输入。

**验收：**逐笔账务可对账，代表性区间可手算和独立参考核对，同输入重跑一致；缺数据不能生成正式绩效，也不能使用单股模拟代替。

### 最后：统一评测和交付运行

建立可重复的环境和数据说明，整理当前改动，逐项修复已登记的类型兼容问题，运行相关测试和必要的全量检查。将实际基准答案、失败样本和真实模型评测纳入版本化管理。

若需要多人长期使用，再给量化主链路接可靠队列、权限、并发控制、限流、来源健康监控、调用费用统计、备份恢复及发布回滚。实际交易执行属于额外范围，需要另行设计，不能因为岗位 JD 涉及交易就默认本项目已经具备。

**验收：**在干净环境能启动、迁移和恢复，真实取数失败可定位，演示脚本可复现；对外宣称的功能和数据范围都有对应记录。

> 当前单股最新研究的主要闭环已经跑通。我的重点取舍是计算和模型解释分开、证据按角色提供、完成报告保持版本，以及缺数据时明确显示限制。动态比较与策略软件链已接通；严格的全市场历史档案、独立绩效参考和额外的量化补证循环仍需继续推进。其中修订和交易限制属于数据工程难点，不能用页面效果或测试数量代替。

## 14. 面试里怎么讲：我认为一个好的量化投研 Agent，最重要的是什么

下面的第一人称段落可以作为面试表达参考。讲述时结合自己实际参与和能解释清楚的部分；“已有实现”和“后续想做”分别表述。

### 先把用户的问题定义清楚

> 我会先确认用户到底想解决什么问题。看公司基本面、比较两家公司、调整估值假设、评价一个策略，还有预测明天涨跌，对数据和评价标准的要求都不一样。我希望系统先把标的、时间、问题类型和输出范围说清楚，再决定用什么工具。

现有实现已经有单股范围识别、证券身份确认、澄清和不支持状态。动态双股比较已接入；更灵活的时间任务规划和三只以上比较仍需扩展。以后如果做涨跌预测，也要先固定预测时点、下一交易日标签和除权处理，不能只加一句提示词就当成预测功能。

### 数据要能回答“是谁、什么时候、什么口径”

> 对我来说，接到一个能返回数字的 API 只是第一步。比如一个 ROE，我还要知道它对应哪个公司、哪个报告期，是累计还是年化、用什么权益口径，以及在研究时点是否已经披露。只要这些条件不同，两个看起来一样的指标就可能不能直接比较。

现有系统会确认证券代码和公司类型，记录数据日期、来源、部分口径与缺项；历史数据还没有达到完整修订链和全市场 PIT 的要求。接下来要把更多口径信息做成可检查的结构化字段，并扩展原始披露核对。

### 把事实、计算、解释和预测分清楚

> 财报里披露了什么，是事实；TTM、PE、DCF 怎么算，是计算；为什么利润增速低于收入增速，是分析解释；明天可能上涨多少，是预测。我会给这几类输出不同的证据和验收要求。这样系统既能发挥模型的理解能力，又能让用户知道每个结论是怎么来的。

当前数值由 Python 计算，模型引用事实和文档证据。DCF 保留假设和方法限制。涨跌概率目前只有讨论方案，尚未开发；以后要增加训练、样本外验证和概率校准，不能把模型自己说的“很有信心”当成已经验证的概率。

### 多 Agent 要有可检查的分工

> 我使用多角色，是想把理解问题、获取数据、分析、复核和组织报告拆成能单独检查的步骤。每个角色有明确输入输出，出错后可以定位是哪一步。后续我还会比较这些角色到底有没有提高质量、增加多少延迟和费用。如果一个角色只是在重复规则，就需要简化它。

当前五角色有实际调用和独立契约，但使用同一个模型，仍可能犯相似错误。Data 的工具选择和 Writer 的写作空间比较受限，目前还没有完成“五角色一定优于单模型”的对照评测，面试时不能把角色数量当成效果证明。

### 检索要为问题提供证据，记忆要有边界

> 我更关心检索出来的材料能不能支持当前问题。比如用户问现金流，我需要找到相关报表和附注，而不是只拿到最近两条碰巧包含公司名字的公告。记忆也一样：可以继承上一轮关注点和参数，但旧数值要带时间，新的研究应该明确是否重新取数。

现有系统已经有证据编号、文本位置、按角色提供上下文和有限父任务记忆。检索目前只覆盖小范围资料，仍需增加按问题选择文档、同一事件去重、时间过滤和反面证据检索。Embedding 或向量库是否接入，应由检索效果和维护成本决定。

### Agent 应该知道何时补查，也应该知道何时结束

> 如果分析发现关键依据不够，我希望它能说清楚缺什么，再调用合适的工具补查。补查以后，要检查有没有增加新信息。如果一直重复找同样的材料，或者已经达到时间和调用预算，就应该带着剩余问题结束。

原底盘已有反馈循环和信息增益控制，量化主链路尚未接入。后续要验证的是“发现缺口后确实补到了有用证据”，而不只是执行轨迹变长。这也是 Agent Loop 值得接入的业务理由。

### 评价效果，要看具体错误和实际收益

> 我会把评测拆开。取数和计算看字段、口径、边界及独立核对；检索看关键材料有没有找回来；模型看结论是否被证据支持、有没有漏掉限制；工程上看成功率、耗时、费用和恢复行为。报告写得流畅，不足以证明前面这些都做好了。

目前已有公式和契约测试、接口与版本测试、真实浏览器流程及部分官方资料核对。后续还要补一组固定业务问题和参考答案，持续测错误引用、错误批准、遗漏风险和资料缺失时的行为；换模型、提示词或来源之后用同一组样本回归。预测能力若开展实验，还需单独建立预测记录和评分，不能沿用报告生成的验收标准。

### 给用户一个可行动、可追问的结果

> 用户看完报告，应该知道哪些事实值得关注、哪些判断证据充分、哪些问题还没查清，以及下一步可以验证什么。改了一个假设后，也应该看得到结果为什么变了。我的目标是减少用户来回查资料和核对数字的时间，让研究过程更容易继续。

现有证据弹窗、参数版本、追问和历史回看支持这条路径。接下来还需要通过用户实际使用，验证报告是否回答了问题，并改善字段重复、说明冗长和缺项提示的可读性。

## 15. 面试里怎么讲：系统可靠性具体做了哪些处理

可以先用一句话开场：

> 我把可靠性分成结果是否有依据、执行失败后能不能恢复，以及出问题后能不能查清楚。当前已经做了几层约束，但还没有把本地演示能力当成生产级稳定性承诺。

### 数据和计算：避免“输入错了，但算得很确定”

> 取数前先确认证券身份，取回来以后检查报告期和适用性。比如银行不直接套工业 DCF，供应商没有给债务字段时也不能自动补零。计算交给确定性代码，并且把公式测试、独立参考核对和同输入复算分开记录。

已实现的措施包括证券搜索与公司资料核对、财报字段处理、披露日期过滤、TTM 与单季差分、明确的 ROE 口径、部分供应商交叉核对和方法不适用状态。正式回测的数据准入会检查历史范围和必要输入，未通过时保留 BLOCKED，不生成正式策略绩效。

这里的披露日期过滤主要约束计算输入；检索侧财务文本尚未逐份执行同样的过滤，不能说所有证据都满足历史时点约束。当前最新财报查询仍缺完整历史修订链，原始公告独立数值核验也未全面完成。因此，“程序能算出值”和“这个指标已经被权威口径验证”仍分别展示。

### 模型输出：同时检查结构、引用和推断

> 我没有只在提示词里写一句“不要胡说”。每个角色都用 Pydantic 约束输出字段和取值；工具只能从白名单选择；结论必须引用当前提供的证据；数字使用事实占位符，直接引用的数字要能在所引材料里定位。最后再用 Verifier 检查推断是否被证据支持。

代码还要求 Verifier 覆盖全部候选结论，Writer 只能选择通过复核的编号。模型不会因为在输出中写了一个 URL 或工具名，就获得新的执行权限；工具端点和执行动作由服务端控制。提示词也明确将文档、记忆和工具结果视为数据，不执行其中夹带的指令。

这里要保留两个边界：数字出现于证据中，只证明找到了这个数，不自动证明它用在正确的主体和期间；当前数字匹配及提示词也不是完整的语义或提示注入防护证明。

美的的真实记录里，模型曾把供应商核对称为“独立核对”，Verifier 仍批准了该表述。指标状态没有因此升级成权威 VERIFIED，但文字审核仍有漏洞。这类失败样本应加入后续评测和规则约束，不能用“第二个 Agent 同意了”解释为绝对可靠。

### 上游失败：关键数据阻断，可选模块说明缺项

> 免费来源可能超时或者少字段，所以我先区分哪些数据是必需的。证券身份和关键价格不成立，就停止出稿；两融、部分财务字段或公告正文缺失，则按模块说明。最新报价刷新失败时，页面清掉旧报价并显示错误，让用户知道当前状态。

目前确实有必要来源失败阻断、可选来源错误记录、UNAVAILABLE / NOT_APPLICABLE 展示和前端报价错误状态。切换股票时还会检查返回结果对应的标的，避免上一只股票的迟到响应覆盖新页面。

有多家来源不意味着已经具备所有字段的自动切源。当前主要是分工采集和部分交叉核对，完整来源健康检查、自动替代与口径仲裁仍需补齐。

### 幂等和版本：防止重复建任务，也保住旧结果

> 前端为一次提交生成请求标识。相同标识、相同参数重试，会返回已经登记的任务；同一个标识换了参数，后端会拒绝。完成的报告保持不变，改参数创建子版本，并清除已经不适用于新数值的旧模型解读。

这样可以处理用户重复点击或提交后响应丢失的常见情况，也能比较调参前后差异。父任务没有完成时，系统不允许建立依赖它的追问。

这里说的是当前本地运行下的任务幂等和已完成结果复用。若外部模型已经处理请求、进程却在保存结果前中断，恢复时仍可能再次调用；目前不能承诺外部 API 的 exactly-once，也不能保证每次失败都不会发生费用。

### 持久化和恢复：以已完成步骤为边界继续

> 我把任务状态、工具和模型调用记录写进数据库，原始资料和产物另存。每次调用开始和结束都留下状态。发生失败后，恢复时先看哪些请求已经有成功结果，能复用的就复用，未完成的步骤重新执行。

服务启动会把遗留的运行中任务标为 INTERRUPTED；用户点击恢复后继续执行。当前不是重启后自动接着跑，也不是接着模型生成到一半的某个 Token 继续输出。

恢复会检查相关实现代码和依赖锁的指纹，模型请求的复用键包含角色、提示词版本、指令、输出 Schema 和上下文。它降低了跨实现版本混用结果的风险，但还不是完整运行环境和模型供应商版本的锁定机制。

已验证过的真实例子是茅台研究日线采集连接超时，页面恢复后复用成功的 Planner、证券解析和 Data 调用，重试失败采集并最终完成。这个例子能说明恢复路径有效，不能推导为所有故障都能自动恢复。

### 资料完整性：确认回看的还是当时那份材料

> 原始响应和报告按 SHA-256 内容寻址保存。读取时重新核对哈希，文本引用还会检查字符位置。这样可以发现资料损坏、引用错位，或者内容已经跟记录不一致的情况。

底层文件存储先写临时文件、同步并校验，再以不覆盖已有目标的方式发布；数据库状态使用事务保存。当前数据库与文件存储不是一个跨存储的原子事务，进程异常可能留下没有引用的文件，需要通过后续清理机制处理。

哈希解决的是内容完整性和寻址问题，不能证明原始数据真实，也不等于完整的防篡改安全体系。金融正确性仍要依靠来源、口径和独立核对。

### 超时和预算：让成本、等待和资源使用有边界

> 我给模型调用、取数和整个任务都设置了限制。失败时只在规定条件下有限重试，达到预算就结束并保留已经完成的工作。这样可以减少一个研究长期占住资源，或者重复调用模型却没有结果的情况。

当前量化主链路可以在代码中核对到这些限制：

| 项目 | 当前实现 | 说明 |
| --- | --- | --- |
| 任务时间 | 外层 600 秒时限 | 达到时限标为中断；后台阻塞 I/O 不保证瞬间结束 |
| 单次角色执行 | 最多两次模型尝试 | 只有可重试错误或输出检查失败等情况才重试，并受总调用预算约束 |
| 模型调用次数 | 达到 10 条模型调用记录后不再发起新调用 | 是本任务的调用限制，不是整个部署的全局限流 |
| Token | 已记录用量达到 26,000 后不再发起下一次调用 | 是软阈值；下一次调用可能使总数超过阈值，超时也可能拿不到实际用量 |
| 模型响应 | 单次设置最多 2,400 输出 Token，超时不超过 120 秒 | 超时还取配置值与 120 秒的较小值 |
| 数据请求 | 连接超时 8 秒，读取超时 18 秒，单响应不超过 3 MiB | 读取超时不等于整个下载一定在 18 秒内结束 |
| 采集资源 | 每批最多 6 个工作线程，归档来源设数量和累计大小预算 | 当前归档预算为 24 个来源键、16 MiB；不等同于精确网络流量计费上限 |
| 活动研究 | 进程内限制一个活动研究任务 | 本地服务的保护措施，尚无分布式队列和跨进程调度保证 |

面试开场不用背这些数字。先说明“为什么要限、在哪里限、触发后怎么处理”，被追问实现细节时再展开。精确费用上限、分布式并发和取消后的资源回收，还需要更完整的实现与验证。

### 可观测和测试：出了问题能定位，也能复现验证

> 我会记录每个角色和工具的状态、输入输出引用、耗时、模型标识、已返回的 Token 用量及错误信息。这样能分清是数据没拿到、计算条件不满足、模型输出不合格，还是前端展示出了问题。测试也会覆盖失败路径，不能只演示成功的一次。

现有验收覆盖了重复请求、参数冲突、恢复、父版本不变、资料损坏、未知引用、非法工具计划、数据缺失、行情断网和页面切换等情况，具体范围以验收记录为准。真实调用轨迹可用于排查；目前没有完整的生产告警、全链路指标平台或稳定性 SLA 验收。

已有测试通过说明这些被测行为有依据。上游是否长期稳定、所有行业口径是否正确、模型是否会产生新的错误，仍需要持续观察和扩充样本。

## 16. 面试可以直接使用的回答，以及容易被追问的取舍

### 一到两分钟介绍设计重点和可靠性

> 我觉得一个好的量化投研 Agent，首先要把数据和结论之间的关系做清楚。用户问一家公司的经营和估值，系统要确认标的、研究时点和指标口径，再去取数、计算和解释。我把数值计算放在 Python 工具里，大模型负责理解问题、选择和解释证据，减少模型直接编数字的机会。
>
> 多角色方面，我拆成 Planner、Data、Analyst、Verifier、Writer，每个角色有结构化输入输出，Supervisor 控制执行。结论要引用实际存在的证据，数字使用事实占位符或者原文定位，Writer 只能采用通过复核的结论。与此同时，我保留独立数值核对的要求，因为多一个模型审核也不能证明金融口径正确。
>
> 工程可靠性上，我做了请求幂等、不可变报告版本、状态持久化、已完成步骤复用、来源哈希校验，以及调用预算和超时。关键数据失败就停止，可选资料缺失则明确说明。发生故障后，可以从记录里查到是哪一步出错，再通过恢复入口继续。
>
> 当前单股主要流程已经用真实数据和模型跑通，但我会明确它的边界：量化自动补证循环还没接入，全市场历史档案还没通过完整准入，本地单进程服务也还没有完成生产级运行验收。这些是后续要继续补的部分。

### 如果问“为什么不直接让一个模型写完？”

> 一个模型完成全部任务当然值得作为基线。我现在拆角色，主要是为了明确数据、计算、分析和审核的接口，便于定位错误和单独评测。但拆开也会增加延迟和费用，所以后面需要做对照实验，保留确实有增量的角色。我不会仅凭五个角色就声称效果一定更好。

### 如果问“为什么没有直接换成 LangGraph？”

> 项目原来已有模型适配、持久化、证据和执行控制，我先复用这些能力，通过结构化契约接量化流程，降低迁移成本。当前固定流程用现有代码可以表达。后续如果分支、补证循环和恢复关系明显变复杂，我会再比较引入图编排框架的收益和改造成本。

### 如果问“数据缺失时为什么不给一个估算？”

> 要看缺的是哪一项。情景假设可以让用户明确输入，并保存成新版本；作为事实依据的财务字段，缺失就不能静默估成零。比如债务漏取会影响 DCF，必须说明缺项或补原始披露。用户应该能分清披露值和自己设定的假设。

### 如果问“你怎么证明模型的回答靠谱？”

> 我能证明它引用了哪份资料、计算使用了什么输入、经过哪些检查，以及哪些样本已经通过验证。我不会把这些说成所有结论都正确。下一步会把已发现的错误批准、错误口径和漏检问题做成固定评测集，比较提示词和模型版本的变化；对于数字，继续补独立参考核对。

### 如果问“为什么报告保存了旧数据，却还说支持最新研究？”

> 新建研究会重新取数，完成后保存当次输入和结果，方便解释和复现。回看历史报告读取的是原版本；最新报价单独刷新，新的研究再创建新版本。这样既可以研究最新资料，也不会让旧报告的依据随着上游变化被悄悄替换。

## 2026-10-11 功能收尾后的接入办法（口语版）

可以这样讲：“我把软件功能和数据齐不齐分开了。比如双股比较，现在用户能直接输名称或代码，双方都重新取数。回测也不只是空页面，内部已经能从选股跑到账本、费用、指标和图表。但如果历史档案不够，我宁愿保存一份有具体缺项的检查结果，也不拿演示收益冒充真实回测。”

现在新增两个明确入口：[最新双股比较](http://127.0.0.1:8839/#/compare)、[完整策略执行](http://127.0.0.1:8839/#/strategy)。[功能与数据接入页](http://127.0.0.1:8839/#/delivery)把操作顺序和剩余数据位置列在一起。

历史数据适配器采用服务端安装的内容寻址包：`package.json` 是结构化档案，`reviews.json` 是独立审核记录，`objects/<sha256>` 是实际原文，`references.json` 可提供独立引擎或权威同口径净值与绩效参考。放在 `QUANT_STRATEGY_PACKAGE_ROOT/<包名>/` 下，刷新页面即可发现。安装不等于准入，通过本次条件核验后才计算。页面不能上传一句 MATCH / STRICT 就放行。

比较层还预留了 `comparison_metrics.profitability` 与 `.quality`。接入工具要提供明确的 TTM 归母 ROE 或同期间净现比，附起止期间、单位、计算定义和已归档来源键。没有这些条件，就不能用累计 ROE 或错期现金流凑数。合同可以在接入页下载。

可靠性上，我区分三件事：手算检查公式；原披露或独立参考检查口径和数值；冻结输入复算检查可复现。当前复算即使 MATCH，缺少外部参考时指标仍是 UNVERIFIED。公司行为有现金应收和待上市股份，不能提前拿应收去买股票；未知限制保留拒单，不自动假设成交。

你现在主要需要做的是页面点击验收，看看结论是否好懂、比较是否符合你的预期。历史完整档案与专业口径审核以后仍需要真实资料和业务判断；开发侧负责接线、映射、采集与测试。暂不需要为了把页面填满而购买 API。
