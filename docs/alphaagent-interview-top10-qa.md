## 1. 你这个多 Agent，到底和写几个提示词、串几个接口有什么区别？

**对应介绍：模型工作流。口语回答，约45—60秒：**

我们确实用提示词区分角色，但区别还在程序层。每个角色有明确的输入、结构化输出、检查点和预算，后一个步骤只能使用经过检查的结果。所以出了问题，能定位是取数、方法选择，还是引用和复核出了错。

深入研究里，Researcher可以提出估值快照、封存证据搜索等工具请求，由后端检查证券、日期和预算，再执行回填。它有自主选择的空间，但不是无限制上网。

当前主链用Python显式编排，便于接入已有任务和历史。代价是分支多了以后维护会复杂。模型主要还是同一个DeepSeek，不能把分角色说成多个独立专家，也不能用Agent数量证明效果。

**备查：**详细稿2.3、2.4、4.1及问答6—10；[详细文档](alphaagent-project-presentation-and-interview.md)。

### 第1题的延伸追问：意图识别是前端做的吗，模型从Planner才开始吗？

**单独口语回答，约45—60秒；与第1题按需选讲，不要求连读：**

从首页正常提交问题时，模型在Planner之前就参与了。前端把问题、所选模式和上一轮理解ID发给本机后端；程序先核实股票，生成去敏上下文，再调用DeepSeek理解任务、期限和指代。程序校验返回结果，前端才负责跳页和预填。

如果识别为投资计划，会先打开表单，用户确认后才取数、封存并发起研究。标准研究主要走Planner、Analyst和Verifier；深入研究在前面增加Researcher。通过后，本地程序算仓位和股数，保存历史，前端画图和展示。

直接进投资研究表单可以跳过首页理解，所以模型从哪一步开始，要看入口和深度。关键词规则仍用于身份、投影和有限回退，但不能把首页正常流程说成纯前端关键词分类。

**备查：**详细稿新增2.3.1—2.3.3及12.3；[完整职责对照](alphaagent-project-presentation-and-interview.md)。

## 2. 你这个知识库算RAG吗？为什么没有向量数据库，知识又是谁选的？

**对应介绍：知识库和检索取舍。口语回答，约45—60秒：**

它有把外部知识和证据放进上下文，再让模型分析的机制，但还没有统一的向量RAG。原文用SQLite全文索引，规则检索用词法匹配、别名和适用周期过滤。

实际投资研究还分两条路径：标准研究先由程序加载八条基础规则，模型在准入范围里选路线；深入研究把已发布候选方法交给Researcher，每只股票最多选三条，并提出假设和反证。所以不能说全靠关键词，也不能说模型每次都在自主翻整本书。

目前只有三十条正式参考规则，我们先把出处、版本和适用性做好。词法检索有语义召回不足的问题，后续要用真实问题比较词法、向量和混合检索，再决定增加哪些组件。

**备查：**详细稿2.5、4.2及问答13—18；[知识与请求流程](alphaagent-knowledge-and-request-flow.md)。

## 3. 金融场景怕模型编数字，你们怎么保证？模型还怎么分析数据？

**对应介绍：模型与本地计算的分工。口语回答，约40—55秒：**

准确说，我们不能保证模型响应里绝不出现数字。它本来就要读行情、比较指标，还要返回引用ID。我们控制的是正式交易数值的来源。

模型负责综合证据、方向和反证；股数、仓位、费用这些由本地程序根据真实数据和账户约束计算。模型输出经过Pydantic结构检查、引用检查、正文检查，再做语义复核，页面组合批准观点和本地计算结果。

这个边界也有缺口，比如字面校验能拦住阿拉伯数字股数和“三成仓位”，却可能漏掉“半仓”。程序公式也可能写错，所以还要靠固定样本和复算验证，不能把程序计算等同于结论一定正确。

**备查：**详细稿2.6、4.5及问答12；[数字与引用检查](../src/marketpulse/quant/knowledge/research_agents.py)。

## 4. 数据来自Tushare就可信吗？实时数据和预测有没有时间泄漏？

**对应介绍：真实取数和封存。口语回答，约40—55秒：**

供应商返回成功，只能说明拿到了响应。我们还检查证券、交易日期、单位、复权口径、财报主体和期间，并区分数据发生时间与系统读取时间。今天读到昨天的数据，不能就标成今天的实时数据。

研究会封存当时可用的资料，财报考虑披露日期，预测绑定目标交易日和签发窗口。缺数、迟签和来源冲突分别记录，不能事后补成正常预测。

资金也要讲口径。现在日频主力资金主要是大单、特大单净额代理，个股分钟资金是特定来源的估算，不代表识别了机构身份。这些措施减少误用，但还不等于全市场严格的历史时点数据仓库，所以原回测准入仍然保留。

**备查：**详细稿12.2、12.6、12.7及问答20—22；[详细文档](alphaagent-project-presentation-and-interview.md)。

## 5. 模型复核一直不过怎么办？是不是最后放宽条件，让它通过？

**对应介绍：银行研究反复待核案例。口语回答，约40—55秒：**

我们处理过一次银行研究反复待核，关键是先查清失败的具体原因。当时复核把“还没达到买入条件”理解成“不能看多”，还出现过各项检查都通过、总评却拒绝的矛盾。

修复时先分开方向和入场条件，让模型只返回事实、方向、交易条件的各项检查，总评由程序汇总。纠错时还要带上它正在修改的上一版分析，避免只给反馈、让模型来回换措辞。

原任务后来在原预算内恢复，新样例也从真实页面完成。但只要事实或条件有一项不通过，仍然拒绝；预算耗尽就保留失败和材料，不能无限重试，也不能用未审核观点充当成功结果。

**备查：**详细稿案例一及问答9、30；[银行复核修复与实源验收](superpowers/plans/2026-10-17-alphaagent-bank-review-recovery-results.md)。

## 6. 页面刷新、网络断开、重复点击，会不会丢任务或者重复扣费？

**对应介绍：幂等、检查点和任务恢复。口语回答，约35—50秒：**

我们把提交、读取和恢复分开了。提交带请求幂等标识，回执丢了先查原任务；刷新只是读任务状态，不会直接重做研究。各阶段保存检查点，恢复时核对证券、输入和版本，匹配才复用已完成步骤。

失败调用和原预算继续累计。已完成报告固定保存，新研究另建记录，后续观察追加进来，因此刷新和新观点都不会静默覆盖旧判断。

但应用幂等不等于供应商严格只收费一次。如果模型已经处理请求，网络却断在返回之前，而供应商没有幂等和结果查询能力，我们就不能承诺绝不重复计费。这个外部不确定性要单独记录和限制。

**备查：**详细稿2.7及问答29、30；[模型调用恢复边界](model-call-recovery.md)。

## 7. 为什么用SQLite加内容寻址文件？完整性核验会不会拖慢页面？

**对应介绍：存储和报告读取优化。口语回答，约45—60秒：**

SQLite负责任务、状态和引用关系，较大的原文、快照和结果按SHA-256寻址保存，方便固定版本和复用相同内容。代价是备份、迁移要保持数据库和档案一致，不能只复制一个数据库文件。

核验确实带来过性能问题。一份评测报告已经生成，读取却超过三十一秒，根因是同一请求里反复读取、校验相同原文。我们在一次请求内复用已核验字节，下一请求重新校验，同一报告的单次读取降到约九秒。

这里优化的是重复工作，保留了核验。这个结果不是全站P95，哈希也不是防篡改公证；如果有人能同时重写数据库和档案，仍要依靠权限和独立备份。

**备查：**详细稿2.7、案例四及问答27、28；[读取优化验收](alphaagent-effectiveness-acceptance-2026-10-19.md)。

## 8. 你们怎么控制Token和调用成本？为什么不直接把预算开大？

**对应介绍：输出截断和预算修复。口语回答，约40—55秒：**

我们遇到过两种不同问题：一种是推理消耗了总输出额度，JSON没写完；另一种是输入按字节预留太保守，实际还有空间却被挡住。所以只调大预算，没有真正解决资源分配的问题。

后来按角色调整推理配置，减少重复上下文，给结构化正文留空间，并固定官方分词器和模板，用真实请求校准预估。机械编号和逐字发布也尽量交回程序。

最终仍按供应商用量累计，调用次数、Token和时间都有边界。失败照样计入，用量未知就保留预留，恢复不能清零。这样既限制无限纠错，也避免把未知成本当成零；估算费用还不能冒充平台实扣账单。

**备查：**详细稿案例二、三及问答11、40；[输出合同与预算验收](alphaagent-contract-budget-acceptance-2026-10-19.md)。

## 9. 不把持仓发给模型，它怎么理解“这只先别卖、再看看另一只”这种追问？

**对应介绍：持仓功能与模型边界的延伸。口语回答，约35—50秒：**

我们把语义理解和账户计算分开。完整问题和持仓先留在本地，本地识别证券和私人片段，形成匿名槽位和去敏投影，再让模型理解任务、指代、期限和关注点，程序核实后映射回证券。

连续追问会利用有限的近期成功语义上下文，所以“第二只”“后者”可以接着理解；成本、股数和现金仍然来自本地结构化资料，聊天理解不会自动修改账户。

复杂表达无法确认时就补充确认，不猜关键数字。去敏本身也会损失语义，需要白名单和回归检查，所以我不会把它说成完全无泄漏，而是尽量减少公开模型完成任务所需的私人信息。

**备查：**详细稿4.6、案例六及问答31；[复杂问题与连续追问验收](alphaagent-semantic-understanding-acceptance-2026-10-19.md)。

## 10. 做了这么多工程，最后到底有没有比原来更准？怎么证明不是增加成本？

**对应介绍：效果评测和默认策略。口语回答，约45—60秒：**

目前我能说工程流程做过实源验收，但不能说增强已经提高了预测准确率。原来的标准流程也使用大模型，所以标准和增强对照，更不能解释成有模型与无模型的比较。

已有一轮把同样封存输入分成标准、动态方法、增加工具和完整增强四组。小样本里，完整增强累计研究耗时多约三成，已知Token多约四成；截至那次验收，没有成熟方向结果证明更准，所以我们保留标准默认、深入按需。

后续要固定样本、截止时间和预算做前瞻配对，分别看完成率、证据质量、到期方向、基线、耗时和费用。失败不换样本，同模型打分也不当准确率。最终要用真实结果判断哪些增强值得保留。

**备查：**详细稿2.9、6.2、6.3及问答35—40；[四组对照与前瞻登记](alphaagent-effectiveness-acceptance-2026-10-19.md)。

## 首页到结果：前端、程序与模型职责速查

此表用于应对“你具体画一下调用链”的追问，不计入上面单题口播时长。以当前首页进入投资计划研究为例；明日预测和其他业务按各自协议分流，不应全部套成Planner链路。

| 环节 | 谁在处理 | 会实际调用大模型吗 |
| --- | --- | --- |
| 输入问题、点击“投资计划”等模式 | 前端保存输入和当前模式，模式作为提示 | 不会，单独选模式不调用 |
| 提交问题理解任务 | 前端请求`/api/quant/questions/understand`；后端检查请求、幂等和容量 | 提交本身不会，随后进入理解任务 |
| 证券核实与语义投影 | 后端取股票目录，匹配证券并建立匿名槽位；按白名单去敏，组织近期语义上下文 | 不会，数据API与规则处理不等于模型调用 |
| 理解任务、期限、否定和连续追问 | 后端发起DeepSeek语义理解请求 | **会，通常早于Planner**；简单首页问句也走这条正常链路 |
| 校验并分发理解结果 | 后端检查结构、目标和任务边界，再还原证券；前端轮询、保存任务选项并导航 | 不会，检查的是上一阶段的模型结果 |
| 投资计划表单确认 | 前端预填股票和期限，用户核对并提交；后端校验新研究请求 | 不会，跳页和表单确认尚不是研究模型分析 |
| 研究取数、指标与封存 | 后端获取真实资料，计算指标和路线准入，固定知识版本，隔离账户资料 | 不会，行情、财报取数和本地计算不靠模型编造 |
| 深入模式的主动研究 | Researcher选择方法、提出假设和反证；程序校验并执行允许的工具，再回填结果 | **会**；标准模式跳过，工具执行本身是程序工作 |
| 路线规划与分析复核 | Planner选已准入路线，Analyst形成观点，程序检查，Verifier复核；必要时受限纠错 | **会**；程序检查与总评汇总不是额外的模型职责 |
| 批准发布与账户试算 | 当前新结构化投资研究由程序固定批准内容，本地核算仓位、股数和费用，保存报告 | 当前这部分不新增Writer调用；旧协议可能不同 |
| 页面展示、刷新与历史回看 | 前端读任务ID、轮询并展示图表；后端核验并读取保存结果 | 正常读取不会重新研究；新咨询、新研究另行计量 |

如果直接打开投资研究表单，可以省掉首页意图理解；标准研究通常从Planner开始，深入研究先Researcher。语义理解失败时，页面明确说明并提供原入口，有限关键词回退只负责安全地进入确认表单，不冒充模型理解成功。

问题理解和正式投资研究分别有`RUN-QU-…`、`RUN-IR-…`记录，要分别看调用和Token。上述“会调用”描述新任务的执行阶段，不表示每次都固定调用一次：已完成任务和匹配检查点可以复用，纠错与补查也可能增加调用。
